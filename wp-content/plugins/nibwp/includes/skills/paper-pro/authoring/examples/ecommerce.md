# Example — a product grid → one component plus a loop

An illustrative walkthrough. The lesson is **telling a component from a query
loop**, which is the difference between a converted design and a working site.

## The situation

A shop page in Paper. One artboard. A hero band, then a grid of nine product
cards, then a newsletter band and a footer. The site runs WooCommerce and Bricks,
and `bricks-pro` is active.

Nine cards in the design. The obvious conversion produces nine cards in WordPress.
That is the wrong answer, and recognising why is the whole example.

## 1. The question that decides everything

The agent asks itself the test from `../core/components.md`:

> What happens when the client adds a tenth product?

If they would edit this page, the cards are a component. If they would add a
product in WooCommerce, the cards are a **query loop**. For a shop page it is
obviously the loop — and so the nine cards in the design are not nine things to
build. They are **one card template plus a query**.

The agent says so before converting:

> Your grid shows nine products. I'll build one card and loop it over your
> WooCommerce products, so new products appear automatically. If you'd rather have
> nine hand-edited cards, say so — but then adding a product means editing this
> page.

## 2. Read one card properly, ignore the other eight

Only the first card gets a full read. The other eight are confirmed structurally
identical and then skipped — which also cuts the node count by roughly two thirds
and turns a 300-node job into a 110-node one. `../core/parser.md` §1.

The card's structure maps onto real WooCommerce data:

| In the design | In WooCommerce |
|---|---|
| product photo | the product image |
| product name | the product title |
| `$48.00` | the price |
| `Sold out` badge on one card | stock status — a **variant**, not a second component |
| star rating | the average rating |
| `Add to cart` | the add-to-cart button |

That badge matters. One of the nine cards is drawn sold out. That is not a second
component; it is one component with a conditional element. Noted as a variant.

## 3. The NDO

- The card is `type: 'component'`, built **once**. No `component_instance` nodes at
  all, because the instances will be generated by the loop, not by the markup.
- The grid container is a horizontal flex with `flex-wrap: wrap` — the only
  responsive key the NDO has, and essential here.
- `$48.00` is 32px, which the size heuristic calls `h2`. It becomes a `p`. The
  product name at 18px becomes an `h3`, because in a product grid the name is the
  heading. Both fixed in the NDO; the size heuristic got both wrong.
  `../core/nodes.md`.
- The star rating is drawn as five vector stars. Vectors become `shape` nodes, which
  render as plain boxes — so this is flagged: WooCommerce renders its own rating
  markup, and the design's stars are decoration to be replaced, not converted.
- One `h1`: the hero headline. Nine product names as `h3`s under it, which is
  correct and which the size heuristic would have made nine `h2`s.

## 4. Assets

One product photo is read as a placeholder and **not** uploaded — real product
images come from WooCommerce. Uploading the design's placeholder shot would put a
stock photo in the media library that someone later mistakes for a real product
image.

The hero image and two newsletter-band graphics do get attached.

This is a judgement the agent states: *"I skipped the product photos — those come
from your products. Say the word if you want them as placeholders."*

## 5. The handoff to Bricks

No Bricks emitter exists (`../builders/bricks.md`), so:

```
preview_convert, builder: "html"
nibwp/load-skill-playbook { skill_id: "bricks-pro" }
nibwp/bricks-pro-html-to-component   dry_run: true  →  fix  →  dry_run: false
```

And `nibwp/bricks-pro-figma-to-component` is **not** an option — it needs a Figma
URL or file key, which Paper has neither of.

What the agent asks Bricks for, explicitly:

- global classes seeded from the `figma-`-prefixed class names, so the card is
  class-styled rather than inline-styled;
- a **query loop** over products wrapping the card;
- dynamic tags bound to title, price, image, rating and stock;
- a condition on the sold-out badge;
- the add-to-cart element from WooCommerce, not a styled div.

That last point is the one worth insisting on. The design's `Add to cart` is a box
with text in it, and the NDO has no href key at all — no link, no button, no form.
Converted literally it is decoration. It has to become Woo's real element or the
grid does not work.

## 6. Verify

Playwright at three widths against the Paper screenshot. The grid wraps 3 / 2 / 1,
which matches the design's intent. Real product data makes the cards taller than
the design's placeholder copy — expected, and better to see now.

## The report

> Draft is up in Bricks.
>
> Your nine cards are **one card in a query loop** over your products, so new
> products appear by themselves. The sold-out badge is a condition on stock status.
>
> Add-to-cart is WooCommerce's real element, not the design's box — the design had
> no link data to convert, so a literal conversion would have been decoration.
>
> The star rating is Woo's own markup, not the design's five vector stars. Visually
> very close, functionally real.
>
> I didn't upload the product photos — those come from your products. Hero and
> newsletter graphics are in the media library.
>
> Cards are styled with Bricks global classes, so restyling one restyles all nine.

## What this example teaches

- Ask what happens when the client adds one more. That answer picks component
  versus loop.
- Reading one card instead of nine cuts the job by two thirds.
- The size-based tag ramp got both the price and the product name wrong. Fix the
  ramp in the NDO.
- The NDO has no links, so every button and nav item is decoration until the builder
  makes it real.
- Do not upload placeholder content as if it were real.
